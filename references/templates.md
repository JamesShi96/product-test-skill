# 模板

## 产品档案 `<档案目录>/product.md`

```markdown
# <产品名> 产品档案

last_tested: <YYYY-MM-DD> @ <commit 短哈希 或 App 版本号>（<局部|整体|评测>）

## 一句话
<这是什么、给谁用、解决什么问题>

## 归属
<自己的产品，代码在 <路径> / 别人的产品，没有代码；竞品：<同类产品，可选>>

## 核心用户旅程（每次冒烟都要走）
1. <旅程名>：<步骤 → 步骤 → 步骤>，成功标志：<用户看到什么>
2. ...

## 功能地图
| 页面/模块 | 主要功能 | 备注 |
|---|---|---|

## 各端测试情况
| 端 | 最近一次测 | 还欠着 |
|---|---|---|
| <网页 / iOS / Android / 小程序 / 桌面 / 命令行 / API> | <YYYY-MM-DD 局部/整体/评测，或"从没测过"> | <没测到的旅程或功能，没有就写"无"> |

## 测试环境
- 本地：<地址 / 启动命令>
- 预发：<地址>
- 正式：<地址>
- 测试账号：<怎么来：本地自己注册 / 在哪里取，不写密码>
- 有真实后果的操作：<付款 / 发邮件 / 扣额度 / 写正式库 / 按次收费的第三方调用 …>

## 测试命令（自己的产品；别人的产品删掉这节）
- 隔离环境：<命令，比如关掉付费调用、用独立数据和端口的启动脚本；没有就写"无">
- 自动化测试：<单元 / 接口 / 端到端各自的命令>
- 健康检查：<地址>
- 测试工具：<比如模拟器叫什么、真机序列号、怎么编译安装>

## 已知问题
- [<日期>] <问题>（<严重度>）
```

## 测试报告 `<run 目录>/report.md`

```markdown
# <产品名> <局部|整体>测试 · <YYYY-MM-DD>

环境：<地址>　版本：<commit>　用时：<分钟>
结论：<一句话>

## 测试清单
| # | 测什么 | 结果 | 证据 |
|---|---|---|---|
| 1 | <改动/旅程> | 通过 / 失败 / 偶现 / 未测 | 01-描述.png |

## 坏了的
### ISSUE-001 <标题>（<严重度>）
- 位置：<页面/功能>
- 复现：
  1. <步骤>（step-1.png）
  2. <步骤>（step-2.png）
- 期望：<…>
- 实际：<…>（result.png / repro.gif）
- Console / 网络：<报错摘要，没有就写"无">

## 测试环境问题（不是产品 bug）
### ENV-001 <标题>
- 现象：<…>
- 原因：<…>
- 影响线上吗：<是 / 否，为什么>
- 怎么绕过的：<比如另起干净库、换端口>

## 用着别扭的
- <用户视角的描述 + 证据>

## 建议（主观）
- <…>

## 对照上次
- 已修好：<…>
- 仍存在：<…>
- 新出现：<…>

## 没测到的
- <内容 + 原因>

## 修复记录（修完后追加）
| 问题 | 改了什么 | 复查结果 | 证据 |
|---|---|---|---|
| ISSUE-001 | <用户能看到的变化> | 通过 / 仍有问题 / 未复查 | <截图或子代理报告路径> |

- 复查中新发现：<问题 + 是否已修>
- 自动化测试：<通过数 / 失败数；失败的是否已换回改动前版本对比过，结论是什么>
- 留着没修的：<问题 + 原因，同步写进档案的已知问题>
```

## 评测报告 `<run 目录>/report.md`

```markdown
# <产品名> 体验评测 · <YYYY-MM-DD>

产品：<地址 / 应用商店链接>　版本：<版本号>　设备：<机型 / 浏览器 + 尺寸>　用时：<分钟>
要回答的问题：<比如"新用户值不值得用""和 X 比哪个更适合 Y 人群">
结论：<值得用 / 能用但有坑 / 不推荐> —— <一句话为什么>

## 任务记录
| 任务 | 步数 | 用时 | 完成了吗 | 卡在哪 | 证据 |
|---|---|---|---|---|---|
| <目标用户真会做的事> | <n> | <分钟> | 是 / 勉强 / 否 | <…> | <截图或录屏> |

## 各维度
| 维度 | 判断 | 理由 | 证据 |
|---|---|---|---|
| 第一印象 | 好 / 一般 / 差 | <一句话> | <…> |

## 做得好的
- <值得学的做法 + 证据>

## 问题
（坏了的用 ISSUE-NNN 写法，见测试报告模板；用着别扭的写用户视角）

## 竞品对比（有对比时）
| 任务或维度 | <产品 A> | <产品 B> | 谁更好 |
|---|---|---|---|

## 建议（主观）
- <…>

## 没测到的
- <内容 + 原因，比如要付费、要注册、没有对应设备>
```

## 交给子代理的说明

交给全新上下文的子代理去测或复查时，说明里要有这些。子代理不知道本会话的任何内容，写全，不要写"像刚才那样"。

```markdown
你是第一次用 <产品名> 的用户，帮我<整体测试 / 局部测试 / 体验评测 / 复查修复>。先读 `~/.claude/skills/product-test/SKILL.md` 和同目录 `references/` 下的文件，按里面"像用户一样测"和安全规则做；模式、档案、报告和收尾由我负责，你跳过。只报告，不修改任何代码和数据，不写 report.md、不改 product.md 和 .gitignore。

- 产品档案：<product.md 绝对路径>（先读，里面有核心旅程和已知问题，已知问题不用再报）
- 环境：<地址>。<它是隔离环境 / 会调用付费服务，最多调用几次>
- 账号：<自己注册一次性账号 / 账号写在哪个文件里>，不要在回复里写密码
- 端和工具：<测哪一端；能用的工具和路径；指定设备：模拟器 UDID 或 `adb -s <序列号>`，不要用 booted>
- 测试清单：
  1. <测什么>：<步骤>，期望：<用户看到什么>
  2. ...
- 复查时：每条按原复现步骤重放，再试一个相近的变体；复查中新发现的问题也要报
- 判断只看界面上看得到的，不读代码来判断对错
- 证据只存到：<run 目录绝对路径>/<端或子代理名>/，文件名带序号和描述
- 回复格式：每条清单写 通过 / 失败 / 未测 + 证据路径；新问题按 位置、复现步骤、期望、实际、证据 写
```
